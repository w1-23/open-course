## 两个动机，一个主题

第 2 章算过一张卡的账：参数量乘以每参数字节数，加上优化器状态与激活，很快就会撞上 80 GB 的 HBM。第 5 章算过另一笔账：单卡算力有限，想更快只能堆卡。课程把这两件事并列成多卡训练的两个动机：

> "1. Your parameters (optimizer state + gradients + activations) don't fit on a single GPU."
> "2. You want to use more GPUs (more FLOPs) to train faster."
> —— `lecture_07.py` 第 38–39 行

这两个动机对应两种完全不同的切法。**省显存**要求把参数或状态切开，**要速度**要求把样本或计算切开。后面所有策略都是这两件事的组合，没有第三种。

课程给全章定的主题只有一句：

> "In both cases, **compute** (arithmetic logic units) is far from inputs/outputs (**data**)."
> "Unifying theme: orchestrate computation to avoid data transfer bottlenecks"
> —— `lecture_07.py` 第 25–26 行

并且明确说这是第 6 章那个主题的第二层：单卡内靠 fusion/tiling 减少 HBM 往返，多卡间靠复制/切分减少跨卡搬运。

> "Last week: reduce memory accesses via fusion/tiling"
> "This week: reduce communication across GPUs/nodes via replication/sharding"
> —— `lecture_07.py` 第 34–35 行

"replication/sharding" 这两个词是全章的骨架。多卡世界里只有两种动作：**复制**（每张卡留一份）与**切分**（每张卡留一片）。而可以拿来切或复制的东西只有五样：

| 对象 | 大小（参数量记作 $P$） | 切它会怎样 |
| --- | --- | --- |
| 参数 | $P$ 个元素 | 前向时别的卡没有权重，必须临时通信补上 |
| 梯度 | $P$ 个元素 | 反向时只有本卡那份，求和必须跨卡 |
| 优化器状态 | $2P$～$4P$ 个元素（Adam 动量+方差） | 更新步骤被摊到不同卡上 |
| 激活 | $b \cdot s \cdot h$ 量级，随层数累积 | 省显存最有效，但要重算或搬运 |
| batch | $B$ 条样本 | 几乎免费，但只扩吞吐不省单卡显存 |

记住这张表，后面每一种 "-parallelism" 都只是在回答：**这五样里，我切哪几样、复制哪几样、为此每步要搬多少字节**。

## 带宽是那堵墙

课程给的硬件层级不是背景介绍，而是全章的约束条件：

> "Typical setup:"
> "- 8 GPUs per node, connected by NVLink to an NVSwitch (B200s' NVLink 5.0 gets 1.8 TB/s; HBM was 8 TB/s)"
> "- 256 nodes per pod, connected by InfiniBand … (~0.05 TB/s)"
> —— `lecture_07.py` 第 219–220 行

家用/经典场景作为对照：

> "- GPUs on same node communicate via a PCI(e) bus (v7.0, 16 lanes => 242 GB/s)"
> "- GPUs on different nodes communicate via Ethernet (~200 MB/s)"
> —— `lecture_07.py` 第 212–213 行

把数字排在一起，墙的形状就出来了：

| 层级 | 范围 | 课程给的带宽 | 相对 HBM |
| --- | --- | --- | --- |
| HBM | 单卡内 | 8 TB/s | 1 |
| NVLink 5.0 + NVSwitch | 节点内 8 卡 | 1.8 TB/s | 0.22 |
| PCIe 7.0 ×16 | 卡到主机 | 242 GB/s | 0.03 |
| InfiniBand | 跨节点（pod 内 256 节点） | ≈0.05 TB/s | $6\times10^{-3}$ |
| Ethernet | 跨机架 | ≈200 MB/s | $2.5\times10^{-5}$ |

![图 7-1　多卡通信的带宽阶梯：HBM 8 TB/s 到以太网 200 MB/s 约 4×10⁴ 倍落差，横轴为对数刻度，数值取自 lecture_07.py 第 212–220 行](figures/svg/ch07-hierarchy.svg)

从 HBM 到以太网约 $4\times10^{4}$ 倍。这个数字解释了本章后面几乎所有的取舍：**能用节点内就不用节点间，能用点对点就不用全归约，能重叠就不用等**。

再建立一个"搬运 1 GB 要多久"的直觉（教材补全，由表中数字直接相除）：

$$
t=\frac{1\ \text{GB}}{\beta}:\quad
0.125\ \text{ms}\ (\text{HBM}),\ 0.56\ \text{ms}\ (\text{NVLink}),\ 4.1\ \text{ms}\ (\text{PCIe}),\ 20\ \text{ms}\ (\text{IB}),\ 5\ \text{s}\ (\text{以太网}).
$$

千亿参数模型的梯度是 $2P=200$ GB 量级（bf16），跨节点同步一次就是秒级；而千卡规模下一次前向反向也是秒级。**通信不是"慢一点"，它是同一量级**——这是本章所有结论的物理基础。

## 集合通信的语言

多卡编程的坐标只有两个：

> "- **Rank**: a particular device/GPU (e.g., 0, 1, 2, 3)"
> "- **World size**: total number of devices (e.g., 4)"
> —— `lecture_07.py` 第 83–84 行

课程把原语分三档，并说明哪一档才是真正天天用的：

> "- Broadcast, scatter, gather, reduce (foundations)"
> "- All-gather, reduce-scatter, all-reduce (workhorse)"
> "- All-to-all (for MoEs)"
> —— `lecture_07.py` 第 87–89 行

八个原语各自的语义与用途（输入输出示例见 `lecture_07.py` 第 91–206 行）：

| 原语 | 做什么 | 单卡视角的输入 → 输出（world size = 4） | 用在哪 |
| --- | --- | --- | --- |
| broadcast | rank 0 复制给所有卡 | $[0,1,2,3]\to[0,1,2,3]$ | 加载 checkpoint 后分发 |
| scatter | rank 0 切片分给各卡 | $[0,1,2,3]\to[0]$ | 理解 reduce-scatter 的台阶 |
| gather | 各卡切片汇到 rank 0 | $[0]\to[0,1,2,3]$ | 理解 all-gather 的台阶 |
| reduce | 各卡归约到 rank 0 | $[0],[1],[2],[3]\to 6$ | 理解 all-reduce 的台阶 |
| all-gather | 每卡都拿到全部切片 | $[0]\to[0,1,2,3]$ | 前向取回被切开的参数 |
| reduce-scatter | 先按位置归约再分散 | 四行 → 每卡一列和 | 反向聚合梯度且分摊存储 |
| all-reduce | 归约结果人人一份 | 四行 → 每卡 $[6,10,14,18]$ | DP 同步梯度 |
| all-to-all | 每卡给每卡发一段 | 平衡时相当于转置 | MoE 的 token 路由 |

最重要的一条恒等式：

> "**All-reduce** = reduce-scatter + all-gather"
> —— `lecture_07.py` 第 169 行

它不是数学趣闻，而是 FSDP/ZeRO 能成立的原因：

> "Breaking all-reduce into reduce-scatter + all-gather allows for flexibility (e.g., ZeRO/FSDP)"
> —— `lecture_07.py` 第 183 行

PyTorch 侧对应 `dist.all_reduce`、`dist.reduce_scatter_tensor`、`dist.all_gather_into_tensor`（第 259、269、279 行），后端在 GPU 上选 `nccl`、CPU 上选 `gloo`（第 547–549 行）。NCCL 本身做三件事：探测拓扑、选路径、发射收发 kernel。

> "NCCL translates collective operations into low-level packets that are sent between GPUs."
> —— `lecture_07.py` 第 233 行

## 把通信折成时间

估算通信开销只需要两个量：要搬的字节数 $V$ 与链路有效带宽 $\beta$，即 $T=V/\beta$。麻烦在 $V$ 怎么算——同一份数据，环状算法下每张卡搬的量并不等于数据总大小。

以 all-reduce 为例（教材补全，依据第 169 行的恒等式与第 325 行的代码注释）。设梯度张量有 $S$ 字节、world size 为 $N$。环状 reduce-scatter 走 $N-1$ 步，每步每卡发送 $S/N$ 字节，合计 $S(N-1)/N$；随后的 all-gather 再走 $N-1$ 步，量相同。所以每卡搬

$$
V_{\text{all-reduce}}=\frac{2S(N-1)}{N}\ \text{字节},\qquad
T_{\text{all-reduce}}=\frac{2S(N-1)}{N\beta}.
$$

这个式子与课程 benchmark 代码的记账方式一致：

```python
size_bytes = data.element_size() * data.numel()
sent_bytes = size_bytes * 2 * (world_size - 1)  # 2x because send + receive, world_size-1 steps in all-reduce
total_duration = world_size * duration
bandwidth = sent_bytes / total_duration
```

> 课程对测量结果的注解：
> "- Effective bandwidth ~ 2 * size_bytes / total_duration"
> "- Independent of world_size"
> "- Independent of topology (ring or tree)"
> —— `lecture_07.py` 第 331–333 行

"与 world_size 无关、与拓扑无关"这个结论值得停下来想：它说的是**有效带宽是一个硬件常数**，你无法通过换算法变出带宽。工程上能做的只有减少搬运的字节数（切分）或把搬运藏进计算（重叠）。

于是"墙"可以写成一个比例。设每步处理 $T_{\text{tok}}$ 个 token、单卡峰值 $F$ FLOPs/s、梯度 $S=2P$ 字节（bf16）。一个训练步的计算量是 $6PT_{\text{tok}}$，摊到 $N$ 张卡上：

$$
T_{\text{comp}}=\frac{6PT_{\text{tok}}}{NF},\qquad
\rho=\frac{T_{\text{comm}}}{T_{\text{comp}}}
\approx\frac{2S/\beta}{6PT_{\text{tok}}/(NF)}
=\frac{2NF}{3\beta T_{\text{tok}}}.
$$

（教材补全：代入 $S=2P$，取 $N\gg1$ 时 $(N-1)/N\to1$。这个量级估算只保留主项，忽略延迟与协议开销。）

$P$ 被约掉了，这是本节最有用的一句话：**DP 的通信占比只取决于每步 token 数与卡数，与模型多大无关**。代入一组具体数字：$F=4\times10^{14}$、$\beta=5\times10^{10}$（InfiniBand）、$T_{\text{tok}}=4.19\times10^{6}$（$b=512$、$s=8192$），得

$$
N=64:\ \rho\approx8\%;\qquad N=512:\ \rho\approx65\%;\qquad \rho=1\ \text{时}\ N\approx786 .
$$

也就是说：在 4M token/步的预算下，纯 DP 扩到 800 卡左右，通信时间就会追平计算时间。想再扩，只有两条路——增大每步 token 数（梯度累积），或者换一种切法（下面五节）。

这个估算只在**带宽受限**区间成立，工程上还有两个它没描述的效应（教材补全，依据第 331–333 行的测量注解）：

1. **小消息看延迟，大消息看带宽。** 上式假设 $V$ 足够大，传输时间线性于字节数。当参数被切得很碎、每层只发几 MB 时，固定延迟（kernel 启动、握手、同步）才是主项，此时"通信量小"并不等于"快"。这就是真实实现要把许多小梯度**打进一个 bucket 再一次发**的原因：把 $m$ 次小传输合并成一次，延迟只付一次。
2. **能重叠就不算墙。** 上式算的是串行时间。如果 all-reduce 能与反向计算重叠（反向是一层算完就能发一层），有效开销可以远低于 $\rho$。这也是 DDP 用 `async_op=True` 与 hook 的原因；本讲的实现为了讲清楚语义，一律用 `async_op=False` 同步等待。

另外要区分两种"大 batch"：$\rho$ 里出现在分母的 $T_{\text{tok}}$ 是**每步**处理的 token 数，用梯度累积（多个 micro-step 攒一次 `optimizer.step`）就能把它变大，而显存不变。代价是每个 micro-step 都要重新做一次前向反向，但无论如何这是把 $\rho$ 压下去最便宜的手段——它不需要任何新的切分，只需要你等得起。当然 batch 也不能无限大：越过临界 batch 之后，同样的算力换来的损失下降会迅速递减 [@large_batch_training_2018]，而临界 batch 本身正是第 9 章要拟合的量之一。

## DP：切 batch

最自然的切法是切数据。课程把它作为第一个完整实现：

> "Sharding strategy: each rank gets a slice of the data"
> —— `lecture_07.py` 第 377 行

每张卡只取自己那一段 batch，其余代码与单卡训练完全相同：

```python
local_batch_size = int_divide(batch_size, world_size)
start_index = rank * local_batch_size
end_index = start_index + local_batch_size
data = data[start_index:end_index].to(cuda_if_available(rank))
```

> `lecture_07.py` 第 407–410 行

与单卡训练的唯一差别，是反向之后多一行梯度同步：

```python
# Sync gradients across workers (ONLY difference between standard training and DDP)
for param in params:
    dist.all_reduce(tensor=param.grad, op=dist.ReduceOp.AVG, async_op=False)
```

> `lecture_07.py` 第 427–429 行

注意这里用的是 `ReduceOp.AVG` 而不是 `SUM`，这不是随手写的（教材补全）。设第 $i$ 张卡上的损失是本地 batch 的均值 $\mathcal{L}_i=\frac{1}{b}\sum_{j\in\text{local}}\ell_j$，我们想要的全局目标是全体样本的均值

$$
\mathcal{L}=\frac{1}{Nb}\sum_{i=1}^{N}\sum_{j\in\text{local}_i}\ell_j=\frac{1}{N}\sum_{i=1}^{N}\mathcal{L}_i ,
$$

即"先各卡求均值，再对各卡取平均"。若用 `SUM`，得到的是 $N$ 倍全局均值，梯度也会大 $N$ 倍，等效学习率随卡数漂移——这是把 DP 从 8 卡扩到 64 卡时最常见的一种"训练莫名发散"。

课程的注记把 DP 的三条性质讲清楚了：

> "- Losses are different across ranks (computed on local data)"
> "- Gradients are all-reduced to be the same across ranks"
> "- Therefore, parameters remain the same across ranks"
> —— `lecture_07.py` 第 382–385 行

由此可以读出 DP 的账本：

| 项 | DP 的取值 |
| --- | --- |
| 切的 | batch |
| 复制的 | 参数、梯度、优化器状态、激活（全都要一份） |
| 每步通信量 | all-reduce 梯度：$2S(N-1)/N\approx 2S=4P$ 字节 |
| 显存收益 | 零：参数量与激活都不降 |
| 能扩什么 | 吞吐（global batch 随 $N$ 线性增长） |
| 何时不适用 | 模型单卡装不下；或 batch 已到临界 batch 上限 |

![图 7-2　三种切法：DP 切 batch 而每卡仍持全部参数、TP 切宽度并靠 all-gather 拼回激活、PP 切深度并在 stage 间点对点传激活](figures/svg/ch07-shards.svg)

"显存收益为零"这一行是下一节的引子。DP 帮你更快，但一点也没帮你装下更大的模型：每张卡仍然持有完整的 $P$ 个参数、完整的梯度、完整的 Adam 状态。按 bf16 权重 + bf16 梯度 + fp32 主权重 + 两个 fp32 矩估计计算，每参数 16 字节；$P=70$B 时单卡需要 1120 GB，这已经远超任何一张卡。DP 的瓶颈不在通信，而在"复制"这两个字。

## FSDP/ZeRO：连状态也切开

课程在本讲末尾留下了明确的接口：

> "Next time: FSDP/ZeRO: use all-gather and reduce-scatter to avoid holding all parameters in memory"
> —— `lecture_07.py` 第 387 行

并在小结里给出了它的通信原语组合：

> "Data parallelism: DDP (all-reduce), FSDP/ZeRO (all-gather + reduce-scatter)"
> —— `lecture_07.py` 第 68 行

FSDP（Fully Sharded Data Parallel）与 ZeRO（Zero Redundancy Optimizer）说的是同一件事的两种实现，核心动作只有三条：

1. **参数按 rank 切开**，每卡只常驻 $P/N$；前向走到某一层时，用一次 all-gather 把该层参数临时拼齐，用完立刻释放。
2. **梯度按 rank 切开**，反向算完某层立刻 reduce-scatter，只保留自己负责的那一片，其余丢掉。
3. **优化器状态按 rank 切开**，每卡只更新自己那 $P/N$ 个参数，然后进入下一轮。

代价是多少？把一次数据并行的 all-reduce 拆成 reduce-scatter + all-gather 之后，字节数和原来一样，因此 ZeRO-1/2 的通信量与 DP 相同（$2S$）；ZeRO-3 因为前向要多做一次 all-gather，总通信量约为 DP 的 1.5 倍（$3S$）。这个"几乎免费"的结论需要一条前提——处于带宽受限区间，此时 $2S$ 已经是下界。三阶段的精确账目、以及"在 8×A100 80G 上最大能装多少参数"，留到第 8 章用课程的表格逐行核对 [@zero_2019]。

这里只需要记住判据：**DP 让训练变快，FSDP 让模型装得下；两者的通信量在同一量级，但 FSDP 用"按需取参数"换来了 $N$ 倍的显存下降**。

## TP：切宽度

如果模型连"一层都放不下"，切数据与切状态都不管用，只能切一层内部的计算。这就是张量并行。课程在实现前先点明了它与 DP 的本质差别：

> "Sharding strategy: each rank gets part of each layer, transfer all data/activations"
> —— `lecture_07.py` 第 441 行

矩阵乘法的分块给了两种切法（教材补全，标准的分块恒等式）：

$$
XW=X[W_1\ W_2\ \cdots\ W_N]=[XW_1\ XW_2\ \cdots\ XW_N],
$$

$$
XA=[X_1\ X_2\ \cdots\ X_N]\begin{bmatrix}A_1\\ A_2\\ \vdots\\ A_N\end{bmatrix}=\sum_{i=1}^{N}X_iA_i .
$$

左式是**列切**：各卡独立算出一段输出，前向不需要通信，拼起来即可（all-gather）；右式是**行切**：各卡算的是部分和，必须 all-reduce 才能得到完整结果。课程实现选的是列切，每层算完就把激活拼回来：

```python
local_num_dim = int_divide(num_dim, world_size)  # Shard `num_dim`
params = [get_init_params(num_dim, local_num_dim, rank) for layer in range(num_layers)]
...
dist.all_gather(tensor_list=activations, tensor=x, async_op=False)
x = torch.cat(activations, dim=1)
```

> `lecture_07.py` 第 453–475 行（节选）

代价很清楚：**参数按 $N$ 切，激活按 $N$ 复制**。每个 Transformer 块有两次需要 all-reduce 的地方（attention 输出投影后、MLP 下投影后），前向两次、反向两次，每次搬 $b\cdot s\cdot h$ 字节（bf16 两字节已含在内时按 $2bsh$ 计），合计每层 $8bsh$ 量级——这个表达式在第 8 章第 43 页被课程明确写出，并与流水线并行的 $bsh$ 直接对比。

所以课程给 TP 的适用条件只有一句，却决定了它的全部工程形态：

> "Tensor parallelism: requires very fast interconnects (e.g., NVLink)"
> —— `lecture_07.py` 第 69 行

这一行切法在 Megatron-LM 里被固定为"列切—行切"成对出现：QKV 与 up-projection 列切，attention 输出投影与 down-projection 行切，于是每个块恰好需要两次归约、且可以合并成一次通信 [@megatron_lm_2019]。

NVLink 1.8 TB/s 对 InfiniBand 0.05 TB/s，差 36 倍；而 TP 的通信量又比 PP 大 8 倍（每层比每 micro-batch）。两个因子相乘，就是"TP 只在节点内做、且一般不超过 8 卡"的全部理由。

TP 还有一个别处没有的优点：**没有气泡**。所有卡在每一层都同时干活，利用率不随 $N$ 下降——这是它敢用昂贵带宽的底气。

## PP：切深度

第三种切法沿层数切：每张卡拿一段连续的层，激活像接力一样往下传。

> "Sharding strategy: each rank gets subset of layers, transfer all data/activations"
> —— `lecture_07.py` 第 486 行

如果每张卡一次只处理一个完整 batch，$N$ 段流水线上同时只有一段在算，利用率是 $1/N$——课程在第 8 章把这个失败模式画成"每张卡只有 $1/n$ 的时间在工作"（`lecture_08.pdf` 第 33 页）。修法是**把 batch 切成 micro-batch**，让不同段同时处理不同的 micro-batch：

> "Break up into micro batches to minimize the bubble"
> —— `lecture_07.py` 第 508 行

```python
micro_batch_size = int_divide(batch_size, num_micro_batches)
if rank == 0:
    micro_batches = data.chunk(chunks=num_micro_batches, dim=0)
...
if rank - 1 >= 0:
    dist.recv(tensor=x, src=rank - 1)     # 等上一段的激活
for param in local_params:                # 只算自己这段层
    x = x @ param
    x = F.gelu(x)
if rank + 1 < world_size:
    dist.send(tensor=x, dst=rank + 1)     # 交给下一段
```

> `lecture_07.py` 第 509–530 行（节选）

流水线的代价是一个**填不满的三角形**：开头 $N-1$ 个时间片里，后面的段在等数据；结尾 $N-1$ 个时间片里，前面的段已经没活干。气泡占的比例是

$$
\text{bubble}=\frac{n_{\text{stages}}-1}{n_{\text{micro}}},
$$

这个式子课程在第 8 章第 34 页直接给出，并配了一句结论："so we need a big batch size"。代入 $n_{\text{stages}}=8$ 就明白为什么：要气泡低于 10%，需要至少 71 个 micro-batch；如果每 micro-batch 装 8 条样本，global batch 就得 568 起步。这种"先填满、再排空"的调度就是 GPipe 引入的 micro-batch 流水线 [@gpipe_2018]。

课程也如实说明了它没做完的部分：

> "Not handled: overlapping communication/computation to eliminate pipeline bubbles"
> —— `lecture_07.py` 第 532 行

这行注释很重要：本讲的流水线实现是**串行**的（算完再发、收到再算），所以它演示的是语义而非性能。真正的 PP 实现会把发送与下一段计算重叠，气泡与重叠的量化是第 8 章的主题。

PP 的经济性来自它的通信量：每传一个 micro-batch 只搬一份激活 $bsh$，与层数无关，而且是**点对点**而非全归约。所以课程说它可以跑在慢链路上：

> "Pipeline parallelism: can work with slow interconnects, but need to work to reduce pipeline bubbles"
> —— `lecture_07.py` 第 70 行

## 一张算得清的账：70B 的四种切法

在把四种策略拼起来之前，先把同一笔账算完。课程在小结里给出了这个领域唯一的三选一：

> "Can **re-compute** or store in **memory** or store in another GPUs memory and **communicate**"
> —— `lecture_07.py` 第 71 行

也就是说，显存不够时只有三种换法：**重算**（不存激活，反向时重做前向，用算力换显存）、**存**（多买显存，用钱换通信）、**搬**（放在别的卡上，用通信换显存）。四种并行策略全部落在"搬"这一支里，区别只在搬什么、走哪条链路 [@transformer_math_2023]。

统一设定：$P=70$B、bf16 通信、$L=80$ 层、$h=8192$、$s=8192$、micro-batch $b=8$，DP/FSDP 取 $N=64$，TP/PP 取组内 $N=8$。梯度字节数 $S=2P=1.4\times10^{11}$。

| 策略 | 每步通信字节（推导） | 链路 | 时间 |
| --- | --- | --- | --- |
| DP（64 卡） | $2S(N-1)/N=2.76\times10^{11}$ B ≈ 276 GB | IB 0.05 TB/s | 5.5 s |
| FSDP/ZeRO-3（64 卡） | $3S(N-1)/N=4.13\times10^{11}$ B ≈ 413 GB | IB 0.05 TB/s | 8.3 s |
| TP（8 卡） | 每层 $8bsh=4.3\times10^{9}$ 元素 ≈ 8.6 GB，乘 80 层 ≈ 687 GB | NVLink 1.8 TB/s | 0.38 s |
| PP（8 段） | 每 micro-batch $bsh=5.4\times10^{8}$ 元素 ≈ 1.07 GB，乘 8 ≈ 8.6 GB | IB 0.05 TB/s | 0.17 s |

三句话读完这张表：

1. **TP 字节数最多**（是 DP 的 2.5 倍），**时间却最短**——因为它在 NVLink 上。带宽差 36 倍、字节差 2.5 倍，净快约 14 倍。这解释了为什么"TP 通信量大"不是缺点，而"TP 跑在 IB 上"才是灾难。
2. **PP 最省字节**。它每个 micro-batch 只搬一次激活，与层数、参数量都无关；一句话，它搬的是 $bsh$ 而不是 $P$。所以 PP 天生适合跨节点。
3. **DP/FSDP 的字节数正比于参数量、与 batch 无关**。正因为与 batch 无关，它只能靠"把 batch 做大"来摊薄——这就是上一节 $\rho$ 里 $T_{\text{tok}}$ 出现在分母的意思。

这张表也解释了真实系统的形态：TP 与 PP 各自解决"一层装不下"和"模型装不下"，而它们一个吃带宽、一个吃 batch，恰好互补。把它们和 DP 拼在一起，就是第 8 章的主题 [@megatron_parallelism_2021]。

## 怎么选

四种策略其实是三个维度的切分加上一个"连状态也切"的加强版。把账本并排放在一起，判据就自己浮现了：

| 策略 | 切 | 复制 | 每步通信量 | 带宽要求 | 显存收益 | 能否扩 global batch |
| --- | --- | --- | --- | --- | --- | --- |
| DP | batch | 参数/梯度/状态/激活 | $2S\approx4P$ 字节（all-reduce） | 中 | 无 | 能，随 $N$ 线性 |
| FSDP/ZeRO-3 | batch + 参数/梯度/状态 | 激活 | $3S\approx6P$ 字节（AG+RS+AG） | 中～高 | 参数与状态降 $N$ 倍 | 能 |
| TP | 宽度（每层内） | 激活、部分权重 | 每层 $8bsh$（all-reduce ×4） | 极高（NVLink） | 权重降 $N$ 倍 | 不能 |
| PP | 深度（层） | 其余层的激活缓冲 | 每 micro-batch $bsh$（点对点） | 低 | 权重与激活都降 $N$ 倍 | 不能，且需大 batch 填气泡 |

四条判据按顺序问下来即可：

1. **单卡装得下吗？** 装得下就别并行参数，直接 DP 或 FSDP-1，通信量最小。
2. **一层装得下吗？** 装得下就优先 PP 跨节点（用便宜带宽），TP 留在节点内。
3. **带宽够不够？** 节点内 NVLink 才考虑 TP；跨节点走 PP 或 FSDP。
4. **batch 够不够大？** PP 需要足够多的 micro-batch 压气泡；batch 上不去时，PP 的收益会被气泡吃掉。

这套顺序在第 8 章会被课程整理成"先 TP/EP 到节点上限、再 PP 跨机、最后 DP 填满"的规则，并用真实模型的并行布局验证。本章只需记住一件事：**没有一种并行是免费的，每一种都在用通信换显存或换速度；判断标准永远是"这次交换的字节数除以带宽，是否小于它省下的时间"**。

四个常见的误判，每一个都能用上面的账本反驳：

- **"TP 通信量比 DP 大，所以 TP 更差。"** 字节数大 2.5 倍，但链路快 36 倍，净快 14 倍。比较的是时间，不是字节。
- **"DP 是免费的。"** 它在显存上收益为零，而且 $\rho$ 随卡数线性增长；扩到一定规模，all-reduce 会吃掉三分之一以上的步时。
- **"PP 可以随便用。"** 气泡是 $(n_{\text{stages}}-1)/n_{\text{micro}}$，batch 上不去时 8 段流水线的利用率可以掉到 50% 以下。
- **"FSDP 通信贵很多。"** ZeRO-3 是 DP 的 1.5 倍字节，而不是数量级；换来的是参数、梯度、状态三项都降 $N$ 倍。

## 本章小结

- 多卡只有两个动作：复制与切分。可切的对象是参数、梯度、优化器状态、激活、batch 这五样。
- 带宽是硬约束：HBM 8 TB/s → NVLink 1.8 TB/s → PCIe 0.24 TB/s → IB 0.05 TB/s → 以太网 0.0002 TB/s，落差 $4\times10^{4}$。
- 集合通信的记账方式是"每卡搬多少字节"：all-reduce 每卡搬 $2S(N-1)/N$，且有效带宽与 world size、拓扑无关，是个硬件常数。
- DP 切 batch，通信 $2S$，显存收益为零；纯 DP 的可扩展上限由 $\rho=\frac{2NF}{3\beta T_{\text{tok}}}$ 决定，$P$ 会约掉——限制你的是每步 token 数与卡数，不是模型大小。
- FSDP/ZeRO 把参数、梯度、状态也切开，用 all-gather + reduce-scatter 换 $N$ 倍显存，通信量与 DP 同量级（ZeRO-3 约 1.5 倍）。
- TP 切宽度，通信 $8bsh$/层，必须 NVLink 级带宽，但没有气泡；PP 切深度，通信 $bsh$/micro-batch、点对点，可用慢链路，但要看 $(n_{\text{stages}}-1)/n_{\text{micro}}$ 的气泡脸色。

**自测**：70B 模型、bf16 梯度、world size 64、InfiniBand 0.05 TB/s，一次梯度 all-reduce 要多久？同样的配置换成 NVLink 呢？如果每步 4.19M token、单卡 $4\times10^{14}$ FLOPs/s，这两个数字各占步时的百分之几？（答案：$S=2P=1.4\times10^{11}$ 字节，$V=2S(N-1)/N\approx2.76\times10^{11}$ 字节；IB 上 $5.5$ s，NVLink 上 $0.15$ s。单卡步时 $6PT_{\text{tok}}/F=4400$ s，64 卡约 $69$ s，于是 IB 占 8%、NVLink 占 0.2%——这就是"TP 必须待在节点内、DP 用 IB 也不疼"的算术来源。）
